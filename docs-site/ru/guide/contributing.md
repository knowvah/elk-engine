# Участие

Сначала прочитайте [Обзор](/ru/guide/overview) и [Правила перевода](/guide/translation-rules). Java на
зафиксированном коммите является спецификацией; при сомнениях читайте Java.

## Проверки

Запускайте их перед каждым коммитом. Каждая должна пройти.

| Команда                | Что проверяет                                             |
| ---------------------- | --------------------------------------------------------- |
| `npm run format:check` | Форматирование Prettier                                   |
| `npm run typecheck`    | Проверка типов TypeScript (нативный `tsc --noEmit`)       |
| `npm test`             | Набор vitest, включая набор golden-тестов                 |
| `npm run coverage`     | Набор с покрытием 90% строк, ветвей, функций и операторов |

Требуется Node 22 или новее. Установите зависимости командой `npm ci`.

## Тесты неизменяемы

Ожидаемые значения берутся из оракула, векторов JVM или исходного кода Java до написания реализации (AD-13).
После написания утверждение замораживается: падающий тест означает, что реализация неверна.

Если тест может пройти, только если изменить его утверждение, вектор или golden-тест, остановитесь и запишите
случай в журнал решений миссии. Не ослабляйте допуск, не удаляйте случай и не пересоздавайте эталон, чтобы
получить зелёный результат. Эталоны golden-тестов пересоздаются скриптом, никогда не вручную.

## Рабочий процесс

1. Создайте ветку функциональности, например `feature/<short-description>`.
2. Пишите сообщения коммитов как [Conventional Commits](https://www.conventionalcommits.org), например
   `feat(java): add JavaHashMap`. Темы пишутся строчными буквами и не длиннее 72 символов.
3. Откройте pull request в `main`. CI проверяет заголовок pull request как Conventional Commit.
4. Коммиты должны быть подписаны; этого требует набор правил репозитория.
5. Pull request сливаются коммитом слияния.

Каждый файл с кодом содержит заголовок SPDX, `// SPDX-License-Identifier: EPL-2.0`. Его наличие обеспечивает
fitness-тест. Зависимости должны быть совместимы с EPL-2.0.

## Команды документации

| Команда                | Назначение                                                        |
| ---------------------- | ----------------------------------------------------------------- |
| `npm run docs:dev`     | Запускает сайт документации с живой перезагрузкой                 |
| `npm run docs:build`   | Собирает сайт; мёртвая внутренняя ссылка приводит к ошибке сборки |
| `npm run docs:preview` | Локально раздаёт собранный сайт                                   |

Большинство справочных страниц включают файлы из `docs/`. Правьте файл в `docs/`, а не страницу в
`docs-site/`. Диаграммы PlantUML во включаемых файлах рендерятся в SVG и коммитятся в
`docs-site/public/diagrams/`.

## Внешние каталоги

Скрипты и тесты находят соседние рабочие копии через переменные окружения. Значения по умолчанию отсчитываются
от корня репозитория. Эти переменные читают только `tools/` и `test/`; код в `src/` — никогда.

| Переменная       | По умолчанию                   | Содержимое                                                  |
| ---------------- | ------------------------------ | ----------------------------------------------------------- |
| `ELK_SOURCE_DIR` | `../elk`                       | Исходный код Eclipse ELK на Java на зафиксированном коммите |
| `ELK_ORACLE_DIR` | `../elk-oracle`                | Отсоединённый worktree и собранный оракул                   |
| `ELK_MODELS_DIR` | `../../eclipse-elk/elk-models` | Корпус elk-models, зафиксированный в манифесте корпуса      |

Для сборки оракула нужны Maven 3.9 или новее и JDK 21 (запасной вариант — JDK 17). Процедуру оракула см. в
разделе [Соответствие](/ru/conformance).
