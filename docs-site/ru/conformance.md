# Соответствие: что означает «совпадение»

@knowvah/elk-engine проверяется на соответствие upstream Eclipse ELK (Java), собранному из
исходников. Компоновка на TypeScript **соответствует** оракулу, если после разбора обеих
как ELK JSON структура и каждое нечисловое значение в точности равны, а каждое конечное число
совпадает в пределах абсолютного допуска `1e-6`.
Компаратор — [`test/golden/compare-json.ts`](https://github.com/knowvah/elk-engine/blob/main/test/golden/compare-json.ts);
этот документ описывает, что он реализует. Правила портирования находятся в
[`docs/translation-rules.md`](/guide/translation-rules).

## 1. Оракул

Оракул (AD-3) — это upstream ELK, **собранный из исходников** в отсоединённом git-worktree
каталога `$ELK_SOURCE_DIR`, который `tools/oracle/build.sh` создаёт в `$ELK_ORACLE_DIR`.
Оба каталога находятся вне этого репозитория; ни один из них не поставляется вместе с ним.

| Элемент                    | Где                                                                                     |
| -------------------------- | --------------------------------------------------------------------------------------- |
| Зафиксированный коммит ELK | `tools/oracle/ELK_COMMIT` (сейчас `8aaa3c145c2a18a38aabbc725aa3791ddc517a76`)           |
| Серия патчей               | `tools/oracle/patches/*.patch`, применяются в лексическом порядке через `git am --3way` |
| Сборка                     | `tools/oracle/build.sh` (Maven 3.9.x + JDK 21; Tycho загружает артефакты p2)            |
| Пакетный запуск            | `tools/oracle/run.sh <outDir> <input>...` или `run.sh --cases <cases.jsonl> <outDir>`   |
| Harness                    | `tools/oracle/harness/ElkOracle.java`                                                   |
| Манифест сборки            | `$ELK_ORACLE_DIR/oracle-build.json` (коммит, патчи, JDK, jar для каждого бандла)        |

**Сборка.** `build.sh` выполняет `mvn -P elk-meta clean install -DskipTests` (компилятор melk), затем
`mvn clean install -DskipTests -Dmaven.test.skip=true` из `build/` в worktree, после чего записывает
jar каждого бандла в области проекта (`core`, `graph`, `graph.json`, `alg.common` и алгоритмы
`layered`, `mrtree`, `radial`, `force`, `disco`, `rectpacking`, `spore`,
`topdownpacking`, `vertiflex`) в `oracle-build.json`. Существующий worktree используется повторно
только в том случае, если он происходит от `ELK_COMMIT`, содержит ровно те темы патчей, что указаны в
`tools/oracle/patches/`, и чист, если не считать результатов сборки; иначе
`build.sh` завершается с кодом `2` и оставляет его нетронутым.

**Запуск.** `run.sh` компилирует `ElkOracle.java` вместе с jar бандлов и
сторонними бандлами (Gson, Guava, EMF, библиотеки Xtext/Xtend) из кэша Tycho p2
(`P2_BUNDLES`, по умолчанию `~/.m2/repository/p2/osgi/bundle`; берётся самая новая
версия каждого). Одна JVM выполняет компоновку каждого входного файла через
`RecursiveGraphLayoutEngine` и записывает `<outDir>/<input basename>.json`
с компоновкой, нулевыми размерами и нулевыми позициями; неизвестные
параметры компоновки опускаются. Сбойный входной файл выводит `ERROR <input>: <message>`; JVM
завершается с кодом `1`, если хотя бы один входной файл завершился ошибкой. Базовые имена входных файлов должны быть уникальны в рамках одного
запуска, так как имя выходного файла — это базовое имя.

**Семантика серии патчей.** Сегодня серия содержит один патч:

| Патч                                                                    | Эффект                                                                                                                                                                                                                                       | Парный seam в TS                                                                                                                                   |
| ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0001-graph.json-seedable-JsonExporter-id-collision-random.patch` (D5b) | `JsonExporter` разрешает коллизии id через `"_g" + Random.nextInt(1000000)`; патч инициализирует этот `Random` из системного свойства `org.eclipse.elk.graph.json.exportSeed` (не задано = поведение ELK). `run.sh` передаёт `EXPORT_SEED=1` | Внедряемый `Random` в порте `graph.json`; ожидает этого порта (шим `Random` в TS уже воспроизводит последовательность: seed 1 даёт 548985, 764588) |

Патчи существуют только для того, чтобы добавлять узко ограниченные seam, делающие поведение JVM и JS
сопоставимым; каждый из них сопровождается парным seam на стороне TS (раздел 4).

**Почему не elkjs?** elkjs — это ELK, скомпилированный GWT. Он не может нести нашу серию
патчей, а эмуляция JRE в GWT отличается от JVM, с которой мы портируем.
Он не используется в качестве оракула.

## 1a. Единица соответствия

**Случай** — это `(algorithm, model, variant)` (D1). В дашборде паритета одна строка приходится на
каждый алгоритм компоновки; папка elk-models и признаки census — это фильтры, а не строки.

**Id случая.** `<tier>/<algorithmSuffix>/<variant>/<modelId>`, например
`native/layered/default/tickets/layered/546_borderGaps`. `algorithmSuffix` — это id алгоритма
без `org.eclipse.elk.`. Для сгенерированных моделей `modelId` равен `generated/<name>`.

**Id модели и источник (D3).** Id модели — это путь в elk-models без расширения.
Случай читает `.json`, если он существует, иначе `.elkt`; `.elkg` (EMF XMI) не читается никогда.

**Варианты (D6).** Именованные наложения параметров в `test/corpus/variants.json`, применяемые к корню:
`default` (без наложения), `direction-right`, `direction-left`, `direction-down`, `direction-up`,
`hierarchy-separate` (`SEPARATE_CHILDREN`), `hierarchy-include` (`INCLUDE_CHILDREN`).

| Tier         | Алгоритм                                                     | Модели                         | Варианты                |
| ------------ | ------------------------------------------------------------ | ------------------------------ | ----------------------- |
| native       | собственный `rootAlgorithm` модели                           | каждая модель census           | все семь                |
| retarget     | каждый перечисленный алгоритм, кроме собственного для модели | каждая модель census           | только `default` (OR-1) |
| generated    | алгоритм, названный префиксом файла                          | `test/corpus/generated/*.json` | все семь                |
| ported JUnit | по миссии для каждого алгоритма                              | случаи upstream JUnit (AD-13)  | как портированы         |

`tools/oracle/run.sh --list-algorithms` выводит список id алгоритмов (сейчас 14).

**Retarget (D2).** Harness устанавливает `org.eclipse.elk.algorithm` для **каждого узла, у которого
есть потомки**, заменяя любое заданное значение, а также `org.eclipse.elk.randomSeed = 1` в корне. ELK
определяет алгоритм для каждого узла отдельно, а узел без этого параметра откатывается к layered. Корень без
потомков получает только seed. Tier retarget пропускает собственный `rootAlgorithm` каждой модели (его
покрывает tier native).

## 2. Критерий соответствия

AD-4 — ровно так, как его реализует `compareLayout(expected, actual, { tol })`:

| Правило                | Поведение                                                                                                                                                                                          |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Допуск                 | Абсолютный, `DEFAULT_TOLERANCE = 1e-6`; конечные числа проходят, если `abs(e - a) <= tol`                                                                                                          |
| Нечисловые значения    | `NaN` и `±Infinity` должны быть в точности равны (`Object.is` или `===`), даже при `tol: Infinity`                                                                                                 |
| Строки, булевы, `null` | Строго равны, иначе `value`                                                                                                                                                                        |
| Несовпадение видов     | Разные виды JSON (`null`, массив, объект, число, строка, булево) дают одно расхождение `type`                                                                                                      |
| Ключи объекта          | Наборы ключей должны быть идентичны: ключ только в expected — это `missing`, только в actual — `extra`                                                                                             |
| Массивы                | Сопоставляются **по `id`**, если каждый элемент с обеих сторон — объект со строковым `id`, а id уникальны на каждой стороне (пустой массив считается индексируемым по ключу); иначе **по позиции** |
| Массивы по ключу       | Id только с одной стороны — это расхождение `structure` по пути `path[id=<id>]`; порядок игнорируется                                                                                              |
| Массивы по позиции     | Разница в длине — одно расхождение `structure`, элементы дальше не сравниваются                                                                                                                    |
| Виды расхождений       | `structure`, `value`, `type`, `missing`, `extra`; `path` похож на JSON-путь (`children[id=n1].x`)                                                                                                  |

Следствия: id элементов, количество элементов, топология секций рёбер и количество
точек излома точны, потому что точны id и длины массивов;
для координат и размеров действует `1e-6`. `formatDiffs` выводит не более 20 расхождений.

**Политика известных расхождений.** Расхождение никогда не поглощается увеличением `tol`
или правкой golden-теста (AD-13). Каждое из них фиксируется здесь с причиной и
тестом или фикстурой, которых оно касается. Допустимые классы:

- **Расхождения `Math.*` на уровне ulp.** V8 и JVM могут отличаться в последнем бите
  `sin`, `cos`, `exp`, `log`, `pow` и им подобных; `StrictMath` в Java определён
  побитово точно, `Math` — нет. Уже встретившийся случай: `nextGaussian`
  по спецификации использует `StrictMath.log`, поэтому `src/java/util/Random.ts` содержит
  реализацию, точную как `StrictMath.log`, вместо `Math.log`. Предпочитайте побитово точный порт алгоритма
  `StrictMath` расширению допуска.
- **Итерация по идентификационным хешам (AD-10).** Итерация по `HashMap`/`HashSet` с ключами —
  объектами с идентификационным хешем недетерминирована уже в самой Java. Запишите место в журнал
  и портируйте с порядком вставки; golden-тесты не должны от этого зависеть.
  Ключи с хешем по значению (String, Integer) обязаны воспроизводить порядок Java.
- **`Random`, инициализированный временем.** При `randomSeed = 0` ELK инициализирует генератор по часам
  (`core/Core.melk:608`), поэтому вывод невоспроизводим. Входные данные golden-тестов должны
  оставлять seed незаданным или ненулевым (seed по умолчанию у layered — `1`).

Конкретные записи (добавляйте только с одобрения пользователя):

| #   | Расхождение                       | Причина                                                                              | Область                                                                                                                                                               | Одобрено                     |
| --- | --------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 1   | Текст сообщения об ошибке разбора | Сообщения ANTLR — артефакты сгенерированного парсера, который никогда не портируется | Некорректный ввод грамматики (`.elkt`, `.elkj`, `.elkr`): совпадать должно только _наличие_ ошибки разбора, а не её сообщение. Корректный ввод должен совпадать точно | D8, пользователь, 2026-10-11 |

**Вердикты.** Каждый случай получает один вердикт по двум отдельным запускам оракула на JVM (D4, D5, OR-2):

| Вердикт            | Значение                                                                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ok`               | Оба запуска выполнили компоновку модели, а выходные файлы побайтово идентичны                                                                                                     |
| `throws`           | Оба запуска выбросили одно и то же исключение: тот же класс и то же сообщение после замены `@[0-9a-f]+` на `@<hash>` (сообщение может быть null, например у `StackOverflowError`) |
| `nondeterministic` | Запуски расходятся (выходные байты, исключение либо один `ok`, а другой `throws`)                                                                                                 |
| `oracle-error`     | Сбой harness (нечитаемый ввод, неизвестный вариант/алгоритм/параметр, потерянная строка результата); недопустим никогда                                                           |
| `timeout`          | Запуск превысил `ELK_SWEEP_TIMEOUT_MS`                                                                                                                                            |

Приоритет: `oracle-error`, затем `timeout`, затем `ok`/`throws`, если запуски равны, иначе
`nondeterministic`. Перед побайтовым сравнением каждый токен `@[0-9a-f]+` в обоих выводах
заменяется на `@<hash>`, как и в сообщениях исключений (D5a; `sameOutput` в `tools/corpus/sweep.ts`).
Причина: программный параметр `debug.discoGraph` у disco экспортирует `...DCGraph@<identity hash>`,
который не удаётся зафиксировать никаким seed. Компаратор на TS применяет ту же замену. О недетерминированных случаях
сообщается отдельно, и они исключаются из счётчиков успешных прохождений в соответствии с политикой
идентификационных хешей, изложенной выше.

Настоящие оставшиеся источники `nondeterministic` (поведение ELK, а не сбои harness; количества приведены в
отчёте о паритете): spore (`ElkGraphImporter.java:169` добавляет разброс через `Math.random`) и `random`
(`randomSeed` по умолчанию 0 не инициализирован для вложенных составных узлов; retarget задаёт seed только корню, D2,
сохранено по решению пользователя). Переименования id `_g<random>` у экспортёра источником не являются: seam-патч
их устраняет.

## 3. Golden-тесты и корпус

AD-5. Эталонные выходные данные закоммичены, поэтому CI не нужна JVM.

| Элемент                | Где                                                                                             |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| Зафиксированный корпус | `eclipse-elk/elk-models` на `commit` из `test/corpus/manifest.json` (не поставляется)           |
| Каталог моделей        | `$ELK_MODELS_DIR`, по умолчанию `../../eclipse-elk/elk-models` относительно этого репозитория   |
| Отобранный набор       | `golden[]` в `test/corpus/manifest.json`: `{ id, path, note }`                                  |
| Refs                   | `test/golden/refs/elk/<id>.json`, по одному на каждый `id` манифеста                            |
| Происхождение          | `test/golden/refs/elk/_meta.json`: `elkCommit`, `patches`, `jdk`, `modelsCommit`, `generatedBy` |

**Сопоставление id с путём.** `golden[].path` задан относительно `$ELK_MODELS_DIR`, а
входной файл — `$ELK_MODELS_DIR/<path>`. `regen-goldens.sh` запускает harness на этих входных файлах
и размещает каждый выходной `<basename>.json` как `refs/elk/<id>.json`.
Пример: id `ptolemy-scrambler` соответствует
`realworld/ptolemy/hierarchical/comm_scrambler_Scrambler.json`.

**Перегенерация** (`tools/oracle/regen-goldens.sh`):

1. Требует, чтобы клон models находился ровно на коммите манифеста (иначе выход с кодом `1`).
2. Требует собранный оракул (`run.sh` нужен `oracle-build.json`).
3. Размещает все refs и `_meta.json` в `test/golden/refs/.elk-staging.*`, затем
   подменяет каталог двумя переименованиями, так что неудачный запуск оставляет старые refs.
4. В `_meta.json` нет временных меток (`builtAt` остаётся в `oracle-build.json`), поэтому
   перегенерация без изменений входных данных в git не меняет ни одного байта.

**Когда перегенерировать:** после изменения `ELK_COMMIT`, серии патчей, набора
`golden[]` или `commit` в манифесте, либо harness. В остальных случаях — никогда.

**Правило ведения журнала.** Каждая перегенерация, изменяющая ref, записывается в журнал с
причиной (id патча или повышение коммита). Refs никогда не правятся вручную. Если
утверждение в TS-тесте или golden-тест можно пройти только изменив их, остановитесь и запишите в журнал (AD-13).

**Census.** `npx tsx tools/corpus/census.ts` ничего не компонует: он запускает оракул в режиме разбора
по каждой модели и сравнивает результат с закоммиченным `test/corpus/census.json` (898
моделей: id, форматы, источник, корневой алгоритм, количества признаков). Код выхода `0` при равенстве, `1` при дрейфе;
`--write` перезаписывает файл. Он работает только в зафиксированном клоне models и прерывается при
сбое harness.

**Сгенерированный корпус (D7).** `test/corpus/generated/<algorithmSuffix>-<shape>.elkr` содержит
конфигурацию grandom с seed; соседний `.json` — это сгенерированный оракулом входной файл без компоновки. Девять конфигураций покрывают
id алгоритмов, которые не использует ни одна модель elk-models: `disco`, `force`, `mrtree`, `radial`, `random`,
`sporeCompaction`, `sporeOverlap`, `topdownpacking`, `vertiflex`. В каждой не более 50 узлов и
нет меток рёбер (`BlindTextGenerator` без seed). Harness называет сгенерированный корень `root`,
потому что `JsonExporter` в ELK разрешает коллизию id суффиксом из генератора без seed. Перегенерируйте
только через `tools/oracle/regen-generated.sh` (промежуточный каталог и переименование; сбойная конфигурация
оставляет старые файлы); повторный запуск без изменений ничего не меняет в git. Порт grandom на TS обязан
воспроизводить эти `.json` файлы байт в байт; golden-тесты алгоритмов от него никогда не зависят.

**Sweep.** `tools/oracle/sweep.sh [--filter <substring>] [--limit <n>] [--shards <n>]
[--out <dir>] [--plan-only]` планирует каждый случай, запускает каждый дважды в отдельных JVM (число шардов
по умолчанию — `min(cpus, 8)` одновременных процессов `run.sh`) и записывает
`$ELK_ORACLE_DIR/sweep/<elkCommit>-<modelsCommit>/{results.jsonl,summary.json,run-a/}`.
`--plan-only` выводит количество случаев по tier и ничего не запускает; `--filter` оставляет id случаев, содержащие
подстроку; `--limit` берёт выборку с равномерным шагом. Код выхода `0`, если ни один случай не `oracle-error`
(`1`); сбой инструмента завершается с кодом `2`. Выходные данные по каждому случаю остаются локальными (AD-5). `ELK_SWEEP_TIMEOUT_MS`
(по умолчанию `30000`, читается только в `tools/`) ограничивает каждый случай; после тайм-аута `run.sh` перезапускает JVM
(код выхода JVM 75) для случаев без строки результата.

**Отчёт о паритете (D9).** `docs/parity-report.md` генерируется из кэша sweep и коммитится:
количества по алгоритмам и вердиктам, с коммитами ELK и models и без временных меток. Перегенерируйте
командой `npx tsx tools/corpus/parity-report.ts --write`; без `--write` команда завершается с кодом `1`,
если закоммиченный отчёт устарел. Никогда не правьте его вручную.

**Тесты корпуса.** `resolveModelsDir()` в `test/corpus/corpus.ts` возвращает причину
`skip`, если клон отсутствует или находится на другом коммите; тесты, которым он нужен,
пропускаются с зафиксированным sha в сообщении. Сегодня `test/golden/oracle-refs.test.ts`
проверяет только закоммиченные refs: по одному на каждый id манифеста, геометрию у каждого узла,
порта, метки и ребра, самосравнение, а также что `_meta.json` соответствует
`ELK_COMMIT`, манифесту и генератору. Теста компоновки TS против оракула
пока нет; он появится вместе с первым портированным алгоритмом.

## 4. Seam-патчи

Seam-патчи изменяют оракул; они редки и всегда сопровождаются парным seam в TS.

1. Внесите правки и закоммитьте в worktree оракула (`$ELK_ORACLE_DIR`) либо подготовьте патч в черновом
   клоне на `ELK_COMMIT`. Чтобы добавить готовый патч в существующий worktree на месте (это сохраняет
   кэши `census/` и `sweep/`, которые удаляются вместе с worktree), примените его с идентичностью
   `build.sh`:
   `git -C "$ELK_ORACLE_DIR" -c user.name=elk-engine-oracle \
-c user.email=oracle@invalid am --3way <patch>`;
   после этого `build.sh` проверяет серию и пересобирает на месте (около 3 минут), так что шаги 4-5
   можно пропустить.
2. Экспортируйте:
   `git -C "$ELK_ORACLE_DIR" format-patch -o tools/oracle/patches <ELK_COMMIT>..HEAD`
   (или только новые коммиты). Файлы называются `NNNN-<slug>.patch`; числовой
   префикс задаёт порядок применения.
3. Добавьте соответствующий seam в TS (то же поведение, внедряемый, в `src/`) с тестами,
   ожидаемые значения которых берутся из пропатченного оракула (AD-13).
4. Иначе удалите worktree: `git -C "$ELK_SOURCE_DIR" worktree remove $ELK_ORACLE_DIR`
   (добавьте `--force`, если результаты сборки делают его грязным).
5. Пересоберите: `tools/oracle/build.sh` (заново применяет серию с нуля).
6. Перегенерируйте: `tools/oracle/regen-goldens.sh`; просмотрите `git diff test/golden/refs`.
7. Запишите в журнал запись с названием патча (`NNNN-<slug>.patch`) и перечнем каждого
   изменившегося ref. Поле `patches` в `_meta.json` фиксирует серию автоматически.

Никогда не оставляйте в worktree незакоммиченных правок: `build.sh` считает такой worktree устаревшим
(код выхода `2`). Никогда не правьте сам `ELK_SOURCE_DIR`.
