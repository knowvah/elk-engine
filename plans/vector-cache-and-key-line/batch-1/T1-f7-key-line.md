# T1: F7 `.elkt` property-key line (typescript-pro)

**Goal:** a validator issue on a property key reports the node-model line (LF, lone CR, CRLF) as Xtext does, proven
by two new JVM validate rows recorded first (AD-13, D5).

## Context

4d T2 moved `.elkt` diagnostic and reference lines to the node model (`nodeModelLineSource(text)`,
`cursor.lineOf`), but `#parsePropertyKey` (`src/graph/text/parser/ElkGraphParser.ts:222-231`) still returns
`{ text, line: first.line }`, the ANTLR line (LF only). That span line reaches `records.noteFeature(entry, 'key',
line)` through `ParseSession.assign` (`src/xtext/parser/ParseSession.ts:50-60`), which is the line the validator
reports for issues anchored on `ELK_PROPERTY_TO_VALUE_MAP_ENTRY__KEY` (e.g. `checkPropertyKey`,
`src/graph/text/validation/ElkGraphValidator.ts:158-163`: `'<id>' is not a layout option.`). The user deferred this
in 4d (journal T2 STOP 1); it is follow-up F7.

## Steps

1. Add the two scenarios; run `nice -n 5 tools/vectors/elkt-vectors.sh "$TMPDIR/elkt"`; copy only
   `graph-text-validate.json` into `test/golden/refs/java/`. The lexer, parse and write outputs must be
   `cmp`-identical to the refs, and the validate ref must gain exactly the two rows (stop 6).
2. Run `npx vitest run src/graph/text/validation`: the lone-CR row must fail on `line` only (red, the expected
   mechanism; journal actual vs expected). If it passes: stop 5. The CRLF row passes.
3. Return `cursor.lineOf(first)` from `#parsePropertyKey`; rerun: green.
