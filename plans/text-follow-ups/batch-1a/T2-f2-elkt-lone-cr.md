# T2: F2 `.elkt` bare-CR diagnostic lines (typescript-pro)

**Goal:** `.elkt` diagnostics and link records count lines as Xtext's node model does (LF, lone CR, CRLF), proven by
new JVM rows recorded first.

## Context

4c found that the shared parse runtime copies ANTLR `token.line` (LF only) into diagnostic lines, while Xtext uses
node-model lines (`InternalNodeModelUtils.computeLineBreaks`). `fix(T11)` added `src/xtext/parser/LineSource.ts`:
`TOKEN_LINE_SOURCE` (the default in `src/xtext/parser/TokenCursor.ts:22`) and `nodeModelLineSource(text)`, which
the `.elkj` parser passes (`src/graph/json/text/parser/ElkGraphJsonParser.ts:199`). The `.elkt` parser still uses the
default; 4b has no vector with a lone CR before a diagnostic (journal 4c rows T12f and fix(T11)).

## Steps

1. Add the scenarios; run `nice -n 5 tools/vectors/elkt-vectors.sh "$TMPDIR/elkt"`; copy only
   `graph-text-parse.json` into `test/golden/refs/java/`. Verify the lexer, validate and write refs are
   `cmp`-identical and the parse ref only gains rows (stop 9).
2. Run the replay: the new rows must fail on `line` only (red, the expected mechanism). Otherwise stop and report.
3. Pass `nodeModelLineSource(text)` in the `.elkt` parser where the `.elkj` parser does.

## Acceptance criteria

- Given a `.elkt` input with a lone CR before an unresolved reference, when the parse replay runs, then the recorded
  diagnostic and link lines match exactly.
- Given a lone CR before a syntax error, when replayed, then the syntax diagnostic's line matches (an ANTLR-recovery
  row that the stop-at-first-error parser cannot reproduce is replayed by presence, as 4c does, and journalled).
- Given every existing `.elkt` parse row, then its replay result is unchanged and the 4b refs other than
  `graph-text-parse.json` are byte-identical.
- Given the commit, then `npm run typecheck`, the colocated tests and `npm run complexity` pass.
